How an idea becomes something people can actually use — four stages, no shortcuts.

01

Research

Every project starts by understanding who the software is actually for, not just what it should do. For Scope3Bridge, that meant reading the GHG Protocol Corporate Standard closely enough to understand why SME suppliers dread sustainability data requests from bigger clients — the forms are built for enterprises with whole compliance teams, not a five-person supplier trying to answer in a spreadsheet. Research is where I find the real constraint, not the obvious one.

  • Domain reading
  • User constraints
  • Problem framing
02

Design

I sketch the data model before I sketch a single screen. Once I know what a "bill" or an "emissions entry" actually is in the system, the UI mostly falls out of that shape. From there it's wireframes, then a small, deliberate set of design tokens — color, type, layout — so the interface stays coherent instead of accreting random decisions page by page.

  • Data modelling
  • Wireframes
  • Design tokens
03

Build

I build backend-first: get the data flowing correctly through a Node.js/Express API into MySQL before touching a component library. That order means the frontend — usually React — is built against real endpoints from day one instead of mocked data that quietly diverges from reality. Features ship in thin, working slices rather than one large unfinished push.

  • Node.js / Express
  • MySQL
  • React
04

Test

I test the boring paths as hard as the exciting ones — what happens when a supplier uploads a malformed bill, or a CO2e calculation gets an empty field. For a tool meant to produce a number a client will report to a bigger company, quietly wrong output is worse than a visible error. I'd rather the system say "I don't know" than guess.

  • Edge cases
  • Manual QA
  • Real data trials
